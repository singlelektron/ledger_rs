# ledger_rs v0.3.0

Release date: 2026-10-08

This release adds portfolio reports, account balance adjustments, easier CSV
migration, and refreshed TUI and Web workspaces. All interfaces continue to use
the same application core and SQLite ledger.

## Reporting and balance management

- Portfolio summaries and monthly trends combine all accounts or selected
  accounts into separate currency groups. CLI, TUI, and Web expose the shared
  report logic; no exchange-rate conversion is performed.
- Portfolio cash-flow reports exclude transfers, opening balances, and
  reconciliation adjustments. Their net change represents transaction cash flow,
  rather than the change in account balances. Months without transactions remain
  visible.
- New CLI opening-balance and reconciliation commands record dated account
  adjustments without creating income transactions. All three interfaces include
  those adjustments in displayed balances; income, expense, category, trend, and
  budget reports exclude them. Adjustment history is preserved in JSON backups
  and account audit snapshots.
- Balance calculations retain recorded adjustments when earlier activity is
  edited or imported. Reconcile again after those changes if the resulting
  balance needs to match a new observation. Opening-balance validation prevents
  duplicate or late opening adjustments on backup restore and database reads.

## Data import and database configuration

- CLI and Web CSV imports accept the external header
  `account,kind,amount,currency,occurred_at,description,category`, matching account
  names and converting positive decimal amounts into exact minor units.
  Validation reports invalid rows and preserves atomic import behavior. Native
  CSV export remains unchanged; importing the same file twice creates duplicate
  transactions.
- CLI, TUI, and Web now share database path precedence: `--database PATH`, then
  a nonempty `LEDGER_RS_DATABASE`, then the platform data directory. Existing
  `./ledger.db` files remain available through the legacy fallback when no
  platform ledger exists. Use an absolute configured path when launching from
  different directories.

## TUI

- A square dark-rose layout adds a numbered page bar, clear context and status
  lines, and responsive transaction rows that keep categories visible.
- Mouse clicks navigate pages, accounts, and detail rows, focus form fields,
  and activate the same save/cancel actions as keyboard controls. Mouse-wheel
  navigation and scrolling complement the existing keyboard shortcuts.
- Press `?` while browsing for help. Forms retain entered values after an action
  fails, switching accounts invalidates stale reports and budget results, and
  page changes reset row selections where needed. Shortcut hints consistently
  show available actions, including refresh.

## Web

- The Web workspace adopts square dark-rose panels, system fonts, and tabular
  amounts. Overview, Reports, and Data navigation remain available on narrow
  screens, with the current area clearly marked.
- Keyboard users can skip directly to main content, follow account shortcuts to
  their form panels, and focus scrollable monthly report tables. Controls have
  visible focus states, and portfolio report regions identify their currencies.
- Transaction history explicitly labels income, expense, and expense refunds.
  Saving an edit returns to the edited transaction, highlights it, and positions
  it below the sticky header on desktop and mobile layouts.

## Upgrade and compatibility

Before upgrading, close running TUI and Web processes and use the existing CLI
to back up the ledger you intend to upgrade. Supply its actual database path:

```sh
./ledger_rs --database /path/to/ledger.db data backup --output ledger-before-v0.3.0.json
```

Keep this backup outside the extracted release directory. Verify the new archive
against its `SHA256SUMS`, extract it, and start the new executable with the same
database path or configured environment variable. Replacing executables does
not replace the ledger.

Opening an older supported database automatically migrates it to SQLite schema
version 5. The migration adds account adjustment storage while preserving
existing transactions and their zero starting baseline. v0.2.0 binaries reject
schema version 5, so retain the backup made before upgrading if you need to
return to v0.2.0. Restore that older backup into a separate empty database with
the older binary; changes recorded after upgrading are not in that backup.

New JSON backups use `format_version: 2` and include dated balance adjustments.
v0.3.0 reads version 1 and version 2 backups; v0.2.0 rejects version 2. Restore
requires an empty target ledger and validates the full backup before writing.
Transaction CSV does not preserve adjustment history.
